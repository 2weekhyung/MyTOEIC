# RC 전체 확장 — 0.2.0

## 범위

기존 Part 5에서 Part 6·7까지 학습 백엔드를 확장했다. 공식 RC 구성은 Part 5 단문 빈칸, Part 6 지문 완성, Part 7 단일·복수 지문이다. 형식 확인은 [IIBC 공식 시험 안내](https://www.iibc-global.org/english/toeic/test/lr/about/format.html)를 사용했고, 공식 예제나 교재의 지문·문제는 복제하지 않았다.

이번 추가 데이터는 직접 작성한 초급 학습 자료다. 공식 난이도·환산 점수와 동등하다고 표시하지 않는다. RC 전체 파트를 공부할 수 있는 문제은행이며 정규 시험 100문항·75분 모의고사는 아니다. 현재는 화면 없는 백엔드 단계다.

| 파트 | 세트/지문 | 문제 | 학습 요소 |
|---|---|---:|---|
| Part 5 | 기존 단문 문제 | 50 | 기초 문법·어휘 |
| Part 6 | 4세트, 각 1지문·4문항 | 16 | 문법, 어휘, 연결어, 문장 완성 |
| Part 7 | 단일 5·이중 2·삼중 1세트 | 30 | 목적, 세부정보, 추론, 의도, 문서 대조, 문장 삽입 |

기존 문법 연습 20개를 포함하면 총 116문항, 선택지 464개와 선택지별 설명, 지문 16개와 한국어 번역이 있다.

## 코드·DB

- V1/V2는 이미 서버에 업로드한 0.1.0 JAR의 SQL과 SHA-256이 같다.
- V3는 기존 question.kind CHECK에 PART6/PART7을 허용하고 `reading_set`, `reading_passage`, `reading_set_question`을 추가한다. MySQL 8.0.19 이상 문법을 사용한다. 확인된 서버 8.0.46과 호환되며 H2·MySQL에서 검증한다.
- V4는 새 RC 콘텐츠를 INSERT-only로 추가한다. 원본은 `content/reading.mjs`, 생성기는 `scripts/generate-reading-seed.mjs`다.
- 기존 학습 테이블·사용자·강의·단어·Part 5는 삭제하지 않는다. 이미 제출한 스냅샷의 새 필드가 없어도 읽을 수 있다.
- 앱 계정의 기존 `SELECT ON mytoeic.*` 권한으로 새 지문을 읽는다. 새 지문 테이블에 INSERT/UPDATE/DELETE 권한은 주지 않는다.
- 문제 페이지는 지문 연결·문서 전체를 IN 쿼리로 일괄 로딩한다. 20문항 조회의 SQL 수 상한을 테스트한다.

새 API는 [API 문서](API.md)의 RC 전체 API를 참고한다. ERD와 테이블 정의서에도 새 관계를 추가했다.

## 신규 설치와 업그레이드

이후 사용자가 로컬 백엔드에서 서버 DB에 연결해 데이터를 넣는 방식으로 변경했다. 현재는 [로컬 연결 절차](LOCAL_SERVER_DB.md)를 우선 사용한다. 아래 서버 JAR 직접 실행 절차는 배포 대안이다. 두 방식 모두 같은 V1~V4 SQL을 사용하며 데이터 설치를 중복해서 할 필요는 없다.

실행 파일은 **`mytoeic-0.2.0.jar`**다. 0.1.0을 서버에서 실행해도 Part 6·7은 생성되지 않는다. FileZilla SFTP로 새 JAR를 서버 전용 폴더에 추가하고 기존 0.1.0은 보관한다. 체크섬 파일은 선택적인 전송 검증 자료다.

실제 서버 적용 전 승인할 변경은 **RC 지문 테이블 3개, 문제 종류 CHECK 확장, Part 6·7 총 46문항과 지문 16개 삽입**이다. 기존 DB가 비어 있다면 V1~V4 전체를 설치하고, V2까지 설치되어 있다면 V3~V4만 적용한다. 서버의 실제 설치 상태를 조회한 다음 적용을 승인받는다.

1. 서버 `mytoeic`의 현재 테이블과 Flyway 이력을 읽기 전용으로 확인한다. 기존 학습 데이터가 있으면 먼저 백업·복원 검증한다.
2. 새 JAR를 업로드하고 무결성을 확인한다. DB 접속정보는 서버 비공개 `.env.migration`에만 보관한다.
3. 사용자 승인 후 이전과 같은 단발성 `--migrate-only` 실행을 **0.2.0 JAR**에 적용한다. 기존 운영 앱이 있다면 호환되는 새 앱으로 교체하는 순서·정지 시간을 승인받는다.
4. 신규 DB의 성공 로그는 4개 마이그레이션 적용, V2 업그레이드는 2개 적용이다. 실제 성공 여부는 로그와 flyway_schema_history의 V4 성공으로 확인한다.
5. `infra/mysql/verify-rc.sql`로 데이터 수·세트 구성을 조회한다. 앱 계정 권한·부트스트랩을 준비한 뒤 API를 실행한다.

실제 네트워크명·IP·서버 비밀번호를 이 문서나 Git에 적지 않는다. 실패 시 자동 DROP·clean·baseline·repair를 실행하지 않는다. 부분 생성 여부와 Flyway 이력을 확인하고 수정 계획을 다시 검토한다.

이 저장소에서의 코드 검증은 실제 서버 적용 승인을 대신하지 않는다. 2026-11-01 사용자 승인을 받은 뒤 실제 서버의 V2 설치를 확인하고 V3·V4를 적용했다. 백업 복원과 기존 행 보존, 재실행 결과는 [서버 DB 적용 기록](SERVER_DB_APPLIED.md)에 정리했다.
